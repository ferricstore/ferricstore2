# Workflow implementation with TDD

The user explicitly requested finishing all remaining implementation and required Elixir test coverage, with TDD and GPT-6.1-sol/max subagents that communicate and review each other. Keep dedicated architecture and performance review across milestones. Follow the active full-completion goal, docs/reviews/workflow-completion-coordination.md and the ordered milestones in docs/implementation-plan.md; do not stop or declare completion after one narrow increment. Later runtime adapters require their predecessor gates. Do not add fake durability/service behavior or mark full workflow parity passing without executed counterparts for all required cases.

Read README.md and docs/architecture.md before proposing changes. Keep the workflow-only scope. Source observations, proposed decisions and unresolved validation gates must be distinguished. Cite source paths and upstream primary documentation. Record disagreements and resolutions in docs/reviews; do not claim independent review unless it happened.

Implementation must follow the dependency allowlist, functional core and safety rules. Architecture changes require an ADR and updates to architecture checks. Do not suppress checks just to pass CI. Preserve backward compatibility only where explicitly included in the parity matrix. All first-party code inherits workspace lint policy and forbids unsafe. Tooling/test-support crates must never enter production dependencies.

Use the explicitly requested subagents, communicate through actual shared-file reads and coordinator relays where direct tools are unavailable, and record reciprocal findings/resolutions in docs/reviews. Agree on API contracts before dependent changes. Assign disjoint write sets; only the coordinator changes shared root policy/configuration or commits/pushes. Do not overwrite a peer's implementation. Record real failing-test evidence before implementation and real passing evidence after it. Never claim TDD from tests written only after code.

The user requires architecture consultation before creating any new file, type/class, module or model. This applies to the coordinator, implementation agents, test/tooling owners and performance probes. Send the architecture agent the concrete paths/names, responsibility, dependencies, API/data ownership and resource implications, and wait for an explicit recorded decision before creation. One decision may approve a concrete named batch; a broad crate assignment or an agent's own interpretation is insufficient. Record approval IDs and approved artifacts in docs/reviews/workflow-completion-coordination.md. Existing artifacts may be edited within their approved contract. Contract changes and newly discovered artifacts require another consultation. When concurrency is full, finish a finite peer task normally and rotate the architecture reviewer back in; do not interrupt peers or bypass this gate.

Group related code by responsibility. When a source module needs several files, use feature.rs with private children in feature/. For a multi-file Cargo integration target, use tests/<target>/main.rs and child modules beside it. Keep single-file modules and integration targets simple; Rust does not require one file per type. Production Rust files stay within 400 physical lines and tooling/integration files within 600, including comments and blank lines. Grouping never bypasses the named architecture consultation or changes a peer's tree without a concrete approved move.

The existing Elixir workflow tests are mandatory acceptance inputs: read docs/workflow-test-parity.md. Preserve source identities, scenarios and assertions in Rust counterparts; do not silently drop cases, weaken assertions or count ignored/deferred tests as parity. tests/reference contains preserved upstream test sources and fixture/manifest data, not a runnable Rust implementation.

Linux and macOS are both required production and validation targets. Keep the core portable and review OS-specific storage, networking, locking, path and performance assumptions explicitly. Record native results separately for each OS; macOS execution does not count as Linux evidence.
