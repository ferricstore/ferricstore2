# Shared transport operations and conformance

Status: proposed design, 2026-10-09. This document owns shared application admission, security, deadlines, memory accounting, lifecycle, observability and acceptance requirements. It implements nothing, changes no preserved Elixir tests and makes no measured performance or passing-parity claim. The [common contract](../transport-design.md), [TCP design](tcp.md), [HTTP design](http.md) and [intent digest](intent-digest.md) own wire details. The [system review](../reviews/transport-system-review.md) records actual independent reviews, received questions and revisions; agreement is attributed only where written or relayed.

## One application boundary

`wf-api-http` and `wf-api-tcp` decode bounded wire requests from `wf-wire` and call the same application service composed by `wf-node`. The adapters receive no raw storage, Raft, clock-authority, transaction or projection capabilities. Domain decisions stay pure; authentication effects, admission, placement, consensus submission, response reservation and outcome reconciliation belong to the application boundary or narrow node-wired security services. Embedded callers must use that boundary too.

Adapter connection/parser limits protect resources before full application admission; they do not create independent tenant or group quotas. One node-wide admission owner accounts HTTP and TCP together. Tenant and group identity come from authenticated scope and authoritative placement, never unchecked client routing hints. Quotas are local resource protection, not a distributed tenant entitlement; cluster-wide quotas require a separate design. Group-local Raft remains the atomicity boundary.

Operational admission caps, current credentials and attempt deadlines never alter a committed entry's deterministic meaning. Replicas apply the same versioned command/schema/domain bounds and committed inputs; they do not re-run local transport quotas, listener policy or caller timeouts to decide workflow effects. A follower resource/storage failure follows the replica-failure contract, not a fabricated domain rejection or empty claim.

Keep durable `request_id`, connection-local TCP `call_id` and workflow `correlation_id` separate. Retries normalize decoded client intent before digesting, and exclude attempt timeout, credentials, `call_id` and raw transport bytes. The application authorizes the current principal before both original submission and retained-outcome lookup. Each ordinary mutation and whole `atomic_group` intent requires a stable request identity; an `independent` batch has no durable outer ID or orchestrator, and every caller-ordered mutation item has its own ID. Legacy no-ID lease/fence tests keep their separate compatibility path without synthetic reused IDs. Both adapters follow the parent's exact DTO names and typed digest grammar rather than define aliases here.

Required mutation `request_scope:{group_id,recovery_id}` binds the intended durable identity namespace before first send. Ordinary mutations and whole atomic_group intents carry it; independent-batch mutation items each carry their own scope with no durable outer scope. An authenticated discovery/placement query supplies authorized stable scope (single-group M4 may use scoped discovery); it grants no Raft membership or routing authority. The SDK persists that scope with request ID and normalized intent before submission and preserves all three on retries. Authoritative placement verifies scope against every touched partition and current recovery identity at admission and again before consensus handoff after queue/poll/forwarding. Missing/mismatched/old scope rejects before this attempt proposes; it cannot be auto-filled or rebound to the latest identity. Discovery racing restore yields a safe rejection, not permission to resubmit a new scope automatically. Request scope is key context excluded from the intent digest; semantic partition arguments remain included. The no-ID compatibility surface retains its original source contract.

## Admission and memory ownership

The required admission order is: bounded connection/header/prefix parsing; bounded authentication; tenant and operation authorization; normalized input size/work validation; authoritative group routing; optional bounded queue/input/state reservation; fair dispatch with one atomic acquisition of execution/cost and worst-case response capacity; deadline-aware execution. A queued request holds no active execution or worst-case output permit while waiting (≤10 ms). Dispatch transfers its existing input/state charges without double accounting; physically coexisting input/decode/copy allocations remain separately charged. Parked waiters have their own bounded phase. No unbounded tasks or lists of blocked permit acquisitions may precede a limit. Attackers do not receive unlimited authenticated work merely by opening streams or pipelining.

Reservations cover owned buffers, decoded values, base64 expansion, pending authentication, queued requests, application state, reserved outcomes, serialized output and stalled socket writes. A buffer has one accounting owner and retains its charge while transferred between adapters and application. Logical byte limits do not claim allocator/RSS limits: implementations must measure allocation overhead, TLS/HTTP buffers, task stacks and retained shared buffers and reserve headroom. Inline payloads remain bounded; deferred blobs cannot become dangling references.

Commands reserve a proven upper bound for their response before submission. Commands with unbounded output cannot be admitted. A slow reader may cause the transport reply to be abandoned, but it cannot prevent persistence, release a still-live consensus task's permit, undo a committed command or turn its result into rejection. Streaming queries use bounded pages/chunks and cannot pin a whole result set; they may release query permits between pages only if consistency and cursor contracts allow it. A retained cursor is not a storage transaction lock.

### Initial operational envelope

All numbers below are proposed starting assumptions for a single node with at least 4 GiB available to the process. They are neither benchmark results nor production guarantees. Admission uses the stricter byte, count and work limit; deployments must scale down when storage/cache/consensus memory leaves insufficient headroom. Final wire limits must agree with the common contract and peer designs.

| Resource | Proposed initial default | Required behavior |
|---|---|---|
| Shared application request/response pool | 256 MiB/node: 128 MiB admitted/queued/parked state, 64 MiB response/control reservations, 64 MiB ingress/authentication | Maintenance, control and waiter slices are inside these totals; reject before allocation/submission when a reservation would exceed a partition |
| Active application work | 256/node, 128/group, 32/tenant, 16/connection | Shared across both protocols; retained consensus work remains charged after reply loss |
| Waiting application work | 128/node, 64/group, 16/tenant, 8/connection; also charged by bytes | Holds only queue/input/state reservation; wait ≤10 ms or remaining deadline; dispatch acquires active/cost/output atomically |
| Aggregate pending calls per connection | 24, including active + admission-queued + parked long-poll calls | At most 16 active and 8 admission-queued; parked calls consume this same total, never 24 additional slots |
| Reconciliation/lease maintenance reserve | At least 26 of the 256 active slots and 7 MiB of the 64 MiB response partition | Ordinary traffic cannot consume this slice; sublimits and authorization still apply; no 10% added on top |
| Accepted external connections | 1,024/node, 64/authenticated tenant; 64 handshakes in flight | TCP connections and HTTP connections share a node-wide count; unauthenticated traffic is globally/source limited |
| Serialized request/response body | At most 1 MiB each per ordinary operation/page, including envelope/base64 | Response limit is min(node profile, operation, authenticated scope, negotiated client receive cap); physical reservation also covers decoded result and encoding copies |
| Opaque decoded bytes / structural input | 256 KiB/value, 512 KiB total/call; depth 16 and 4,096 aggregate fields/items | Independent preallocation/structure/work caps; stricter operation bounds still apply; compatibility scenarios retain reviewed case-specific profiles |
| Parked claim waiters | 128/node, 64/group, 16/tenant, 8/worker, 8/connection; ≤16 registered scope keys/waiter | Independent ledger outside the 10 ms ordinary admission queue; included in connection pending ≤24 |
| Parked metadata/wake capacity | 8 MiB inside the 128 MiB request-state partition; ≤8 KiB metadata/waiter, scope key ≤256 bytes | Includes registration/timers/coalesced wake tokens and bounded wake queue; reject a larger registration before parking |
| Wake dispatch | At most 8 dispatch tasks/node, 32 ready waiters/batch; one coalesced token/waiter | Recheck fairness/auth/deadline and acquire full active/response reservation on wake; no unbounded task per notification |
| Handshake/authentication duration | 5 seconds maximum | Includes waiting for bounded verification services; no preauth queue can defeat it |
| External attempt deadline | 5 seconds default, 30 seconds maximum | End-to-end attempt budget, not five seconds per internal stage |
| Response write | No-progress watchdog ≤5 seconds; absolute duration ≤remaining attempt budget | No new 30-second allowance after apply; abandon delivery without changing durable outcome; free memory only when no task references it |
| Graceful drain | 30 seconds default | Stop admissions first; preserve/resolve accepted work where possible, then stop replicas under their durability contract |

All per-tenant/group limits and fairness are local per node. More connections to one node do not multiply its tenant allowance; contacting several nodes can multiply local allowances until a separate cluster-wide entitlement is designed. Dispatch counters/byte/work reservations acquire atomically: 256 active slots do not promise room for 256 simultaneous 1 MiB replies in a 64 MiB response partition. The stricter actual reservation wins. Bounded queued input remains charged separately without owning active/output capacity. TCP 4 MiB/session input/output ceilings are lazily acquired maxima, never preallocated capacity promised to each of 1,024 sockets. Connection/control/TLS baseline allowances are charged before acceptance and may reduce the effective connection count. TCP's 16 KiB control allowance per accepted session uses the response/control partition, with a bounded aggregate slice; HTTP control/parser allocations require equivalent accounting. Emergency bounded errors cannot consume maintenance capacity or allocate after an exhausted pool; close when safe delivery cannot be reserved.

These caps may constrain an advertised batch/claim count. Reserve the complete serialized claim result, including base64 and metadata, before proposing. For example, 32 payloads of 32,000 bytes exceed 1 MiB after base64 alone; accepting such a shape and discarding fields after commit is invalid. Reject an indivisible incompatible mutation before proposal or select an explicitly supported larger profile. Semantic source scenarios keep their case-specific compatibility/limit mapping and future acceptance gate; deployment caps never authorize deleting or weakening an included assertion. A partial result is permitted only by a declared operation contract. FIFO's deep lane-head tests require finding the eligible head in the same call, irrespective of a follower scan budget.

Use tenant-fair round-robin dispatch with per-group concurrency gates. Reads, claims and mutations have explicit work weights; an attacker cannot evade fairness with many TCP `call_id`s or HTTP streams. This is a proposed scheduler policy, not a global ordering/fairness guarantee. Raft decides command order. Do not wait while holding locks needed by another path; an unavailable dispatch reservation leaves work only in its bounded queue, without a separate spawned semaphore waiter. Queue, execution and parked phases each acquire their own resources atomically rather than create cyclic per-tenant/per-group dependencies. Overload before submission is a definite non-submission; after submission it is never recast as ordinary overload.

### Parked claims and wake ownership

Perform authorization and retained-ID reconciliation before registering a long-poll waiter. A waiter owns only bounded authenticated context, deadline, normalized intent, scope registration and coalesced wake/timer state. It owns neither a durable lease, mutation execution slot nor a maximum-size response reservation. Its charged metadata remains live until removal. Broad authorized scopes use bounded compact scope keys rather than one registration per workflow/partition; if the selected operation cannot fit its declared scope representation, reject explicitly rather than silently narrow its scope.

Register/check/wake/recheck closes missed notifications; a bounded periodic due check supplies progress if hints coalesce. Proposed maximum recheck interval is 250 ms with bounded dispatch; it is not an eligibility-to-claim latency guarantee. Wake scheduling uses the same tenant/group fairness and metadata pool, not an unbounded list of pending tasks. On wake, recheck credential expiry/revocation, scope, deadline and retained outcome, then atomically acquire normal execution/work/output reservations. Insufficient reservations do not imply an empty durable claim.

One logical retained claim outcome finalizes a request ID, including a committed empty claim. Physical retransmission/failover may produce duplicate Raft log entries for equivalent intent; apply checks retained identity before claim selection and replays the original outcome without acquiring another lease, minting another fence or duplicating history. This is not an at-most-once-log-entry guarantee. Later polling uses a fresh independent ID only after the known finalized result. An unsubmitted cancelled/expired waiter returns an attempt-local `not_submitted` wait result. Proposal races follow unknown-outcome handling. HTTP/TCP capability discovery must agree about enabled long-poll modes at a rollout; disabling a mode is explicit. The worker reserves handler capacity for unknown claims until reconciled and, before acting on a replayed successful claim, obtains strong current ownership/revision/fence/recovery evidence. An old retained success or elapsed wall deadline alone does not authorize current execution. A strong check cannot prevent later reclaim/cancellation; subsequent mutations still require guards and external effect receivers need their own fencing/idempotency.

## End-to-end deadlines and unknown outcomes

Use a local monotonic attempt deadline established when the bounded request header is accepted; include body receipt, authentication, admission queue, routing, proposal, apply, persistence and response delivery. TCP partial headers and HTTP headers have absolute bounded progress/assembly watchdogs starting before header completion; a client cannot avoid its attempt deadline by never finishing the header. Handshake has a separate watchdog. A timeout field decoded later can shorten the established budget, never restart it. Forward only remaining budget to any trusted internal forwarding service. Never reset a retry/redirect's remaining attempt budget and never accept a client wall timestamp as the deadline clock or lease authority. Deadline, cancellation and overload are effect-boundary policies; committed domain time comes from the existing time/consensus contract.

| Application phase | Cancellation/timeout meaning |
|---|---|
| Before consensus handoff, with proof no submit occurred | Stop work, release owned reservations and report definite non-submission |
| Submission dispatched or handoff may have occurred | Stop waiting/delivery if needed; report unknown outcome unless a durable outcome has been obtained; keep identity, budget ownership and supervised completion |
| Durable deterministic rejection or applied success observed | Preserve/return that durable outcome; late delivery does not change it |
| Response delivery interrupted after durable outcome | Client may know only unknown outcome; retained outcome remains queryable under current authorization |

Cancellation cannot undo committed writes. A durable workflow cancellation command is distinct from cancelling a socket or request task. Failed writes/slow readers do not authorize compensating mutations. Cancellation control acknowledgement is separate from the target's one final response; the shared state owner arbitrates cancel/known-result/unknown races. TCP's selected serial lanes do not establish order across lanes, connections or HTTP, and never determine workflow FIFO. An unknown submitted outcome permanently retires that lane for the connection; no RESUME frame exists. Reconcile before dependent work on a new lane/connection rather than reopening the retired lane.

Non-submission is attempt-scoped. A rejected retry, cancelled waiter, auth denial, overload or drain response proves only that this attempt did not submit; an earlier same-ID attempt may still commit or have committed. A not-found outcome lookup is not proof a proposal is absent from the Raft log or cannot commit later. Resolve uncertainty using authoritative request-status semantics or an equivalent retry with the same request identity and intent, within the documented dedup retention window. A new ID can duplicate the operation. Client-side HTTP/TCP retry logic must preserve this distinction, and reconcile across protocols identically.

Uncertain retry preserves the original request scope too. Incompatible recovery rejects this attempt before submission; it does not disprove an earlier outcome in the old namespace. Lost first replies cannot be the only way the SDK learns its namespace. After disaster restore or incompatible placement, a new ID/scope/intent requires explicit reconciliation or an operator/application decision; the client never silently upgrades recovery identity to continue an uncertain operation. Restore fencing still must prevent old replicas/workers from acting as current authority; a wire scope check alone does not prove disaster-recovery safety.

### Common outcome/error decisions

These names follow the parent common contract; HTTP may wrap the same fields in an RFC9457 problem, while TCP adds its frame correlation. Every structured result includes `schema_version`, `outcome` and `submission`; mutation responses echo `request_id` and original `request_scope` when available, including not_submitted/unknown. Common error identity is `error.code`; human text is bounded/redacted. Retry instructions use `retry.action` and optional bounded `retry.after_ms`, never an unqualified retryable boolean. Position is `{group_id,recovery_id,index}` and exists only with actual durable/read evidence.

| `outcome` / `submission` | Application meaning | Common code/retry mapping; HTTP presentation |
|---|---|---|
| `applied` / `durable_outcome` | Original mutation result durably applied, including a committed empty claim | Data + retained position; no mutation retry needed; HTTP 200 |
| `rejected` / `durable_outcome` | Deterministic rejection committed/persisted with outcome and applied position | Specific domain code such as stale guard; `retry.action:"none"` for that unchanged intent; HTTP 409/422 according to code |
| `not_submitted` / `not_submitted` | Coordinated proof this attempt could not propose | Schema/auth/bounds/capability: no automatic retry; admission/leader referral may give `retry_same_request` hint; HTTP 400/401/403/413/429/501/503 as appropriate |
| `unknown` / `may_have_been_submitted` | Handoff may have occurred and no durable outcome is known | `error.code:"outcome_unknown"`, `retry.action:"lookup_or_retry_same_request"`; HTTP 504 or typed 503/500 as cause permits; status alone is insufficient |
| `read` / `not_applicable` | Ordinary query or outcome-lookup response, including typed read error | Actual consistency/watermark or read-error code; HTTP 200 or documented query-error status; no new mutation implied |

Malformed TCP framing may prevent any valid envelope from being identified: send only a reserved bounded protocol error if possible, otherwise close, without asserting a result for outstanding calls. HTTP gateway-generated errors, partial responses and transport EOF are not trusted application outcomes.

Outcome lookup's `applied/rejected/not_observed/expired/incompatible_recovery/unavailable` are `data.state` values, not replacement outcome/submission pairs for the lookup attempt. A found row nests the retained mutation outcome/position. Required group/recovery identity prevents post-restore ID reuse from resolving in the wrong namespace. Report `expired` only if authoritative retained expiry metadata proves that status; otherwise return `not_observed` with `retention_guarantee:"unknown"`. Absence alone proves neither expiry nor historical nonexistence. The common retained-window field is `outcome_retained_until_ms`. Its window must cover the advertised reconciliation/retry horizon; metadata retention/frontier/tombstone policy, expiry cutoff and post-expiry refusal to promise original outcomes remain gates before SDK automatic replay. A current auth/admission denial during lookup does not settle an earlier mutation.

No request-supplied assertion that it is idempotent, read-only, admin, a specific group member or entitled to a lease bypasses application classification/authorization. Durable fences and lease guards remain separate from principal authentication. Already-accepted command outcomes preserve their original committed inputs despite later deadlines; current credential revocation restricts lookup and future requests without rewriting history.

## Security and network isolation

Proposed production profile is TLS1.3 for external TCP and HTTP. TCP selects ALPN `wf-tcp/1`; HTTP selects only its declared `h2`/`http/1.1` profile, with no protocol sniffing, failed-TLS downgrade or shared Raft listener. A plaintext loopback development profile requires explicit configuration and never accepts downgraded production credentials. Use reviewed rustls integration and safe public APIs; dependency versions/features/provider/MSRV still require freezing. TLS configuration, certificate/key loading and verification live outside `wf-domain`; no custom cipher, TLS parser, direct unsafe codec or unchecked byte cast is justified.

Disable early data on all client APIs. TLS1.3 does not make 0-RTT application effects replay-safe ([RFC8446, replay discussion](https://www.rfc-editor.org/rfc/rfc8446.html#appendix-E.5)). The inspected [rustls ServerConfig](https://docs.rs/rustls/latest/rustls/server/struct.ServerConfig.html) exposes `max_early_data_size=0` to disable it and documents ALPN configuration. Keep half-RTT data and key logging disabled. Use separate ticket/session-resumption stores and server configurations for client, Raft and administration listeners with distinct identities/audiences; rustls warns that shared resumption across different client-verification policies can undermine authentication. These are application deployment policies, not a rustls proof of our tenant isolation.

Authenticate principal plus tenant scope through configured mTLS identity and/or bearer credentials. TLS connection identity may be cached for the connection lifetime; operation/tenant capabilities and expiry are checked for each admitted request and again before dispatch after waiting/parking. Authentication verification must have bounded cache entries, a bounded queue, bounded refresh calls and a failure policy; verification outage fails closed rather than guessing from an expired allow result. Rotation/revocation refresh deadlines are deployment assumptions that must be documented. TCP refresh reconnects without changing an in-flight session principal; HTTP validates each bearer attempt. Reject spoofed forwarded identity or routing unless received through the explicitly trusted proxy boundary. Do not put credentials, payloads or lease tokens into tracing fields, HTTP URLs, reflected errors or unbounded metric labels.

Capabilities name workflow operations and tenant scope. Workers receive only claim/extend/report/query permissions they need; policy installation, broad cancellation, retained private payload access and administration require separate permissions. Worker identity and workflow ownership cannot be forged by a supplied string. Request lookup must not reveal another tenant's records, retained errors or digest existence. Public readiness/liveness diagnostics expose bounded coarse state; detailed health, topology, logs, backup, membership and restore controls require privileged identities.

External client transports and Raft use separate listeners, credentials, authorization audiences and network policy. Client TLS credentials cannot authenticate a cluster member, even on a shared host. The external adapters expose no Raft RPC, snapshot installation, vote, membership or storage handle. Consensus peer authentication and versioning are distinct adapter gates; shutdown/overload must reserve network/runtime capacity for peer heartbeats and apply so client saturation cannot starve elections. Client-supplied leader hints, redirect targets, forwarded tenant headers or certificate names cannot create an arbitrary network dial/credential leak.

## Blocking and graceful shutdown

Async I/O does not bound CPU work. JSON/base64 parsing, cryptographic verification, serialization, storage calls and compression may monopolize an executor or blocking pool. Bound input first, reserve execution slots before starting work and measure time/memory cost. Proposed client decode/auth blocking gate is 8 active and 32 queued jobs/node, inside the ingress/auth pool and request deadline; storage/consensus uses separately bounded owners. CPU gate admission precedes spawning, not merely setting a large runtime thread maximum. Any outstanding job remains charged after the caller stops waiting.

The inspected [Tokio spawn_blocking documentation](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html) states that started blocking tasks cannot be aborted, excess tasks queue at the thread limit, and shutdown timeout stops waiting without cancelling them. [Tokio timeout](https://docs.rs/tokio/latest/tokio/time/fn.timeout.html) can be exceeded by work that does not yield. Therefore timeout is a waiting policy, not a CPU/fsync bound; supervision and permit ownership must follow underlying work. Tokio documentation observed version 1.53.2 and rustls 0.23.45 during the bounded check are discovery evidence, not selected dependency pins. Separate consensus persistence/snapshot capacity from client CPU work and prove cancellation-safe owners in the future spike.

Shutdown has shared application phases. In draining, remove ordinary readiness, stop new ordinary/create/claim admission and remove unsubmitted parked claim waiters. Existing listener connections or a deployment-selected maintenance ingress may still submit only bounded currently authorized lease maintenance, reporting for already-owned work and outcome reconciliation using the maintenance slice. Adapters ask the application classification; they cannot independently whitelist a client-supplied maintenance flag. Drain submitted work/deliverable outcomes and workers' existing handlers up to the budget. In full stop, stop all client admissions/listeners, then consensus/projection/storage in durable order. The node must retain a defined maintenance path during drain; closing every listener before it would defeat reporting. No new claim is allowed merely because a worker is authenticated.

At the hard deadline, replies may be lost and become unknown; unresolved accepted work is never relabeled rejected. Started blocking jobs may outlive a runtime wait timeout. Final process termination is a crash boundary handled by recovery/unknown-outcome tests; a 30-second drain target does not promise every fsync/task was interrupted or completed safely. Crashes remain part of the acceptance contract, not a graceful-shutdown assumption.

## Tracing and latency evidence

Each effect-boundary request has spans for receive/body, authentication, queue, routing, consensus wait, apply/persistence, encoding and write. Distinguish attempt identity, durable request identity, transport-local call identity, tenant/group scope under bounded/redacted policy and applied position. Core decision functions return facts rather than emit telemetry. Record input/output/reserved bytes, active/queued/rejected counts, queue duration, storage stall, projection watermark lag, unknown outcomes, retry reconciliation and shutdown leftovers.

Proposed SLO planning target: admitted small mutations and authoritative point reads, at most 16 KiB logical input/output, should aim for p99 ≤ 50 ms in a healthy same-region three-node deployment, at ≤ 60% of measured sustainable mixed-load capacity, with persistent storage meeting the measured baseline and no leadership change/snapshot installation. This is an unvalidated design target, not a promise. Also report all offered attempts, overload/rejection rate and admitted fraction; an excellent admitted-only p99 obtained by rejecting most work does not meet a service objective. Cross-region, large payload, projection scan, failover, stalled disk and overloaded traffic require separate envelopes and recovery measurements. No universal p99 is derived from choice of Rust/Tokio/TCP/HTTP.

Use an open arrival schedule that timestamps intended arrivals before admission and records client scheduling lag. Do not measure only a closed loop that stops offering work during stalls. Report intended-arrival-to-outcome and actual-send-to-outcome separately, with queue/rejection/timeout distributions, p50/p95/p99/p99.9, RSS/high-water allocation and offered/completed rates. Never omit failed attempts or silently cap their observed latency. [HdrHistogram's correction methods](https://docs.rs/hdrhistogram/latest/hdrhistogram/struct.Histogram.html#method.record_correct) generate synthetic interval-based samples; if used, report the assumed interval and raw data and apply correction only once. Its saturating recording APIs can hide outliers, so overflow must be explicit. Correction cannot recover unrecorded errors or substitute for an open offered-load schedule. Use equivalent workload/consistency/durability/payload/connection settings across TCP and HTTP; include both alone and mixed load, fair-tenant isolation and slow-reader adversaries. All measurement procedures and evidence are future gates, with no measurements performed here.

Separate attempt-response latency from original-arrival-to-known-durable-outcome, including reconciliation/retries. A fast unknown reply is not a successful mutation completion. Report unknown-to-resolution time and unresolved/censored fraction at the observation cutoff; do not discard those operations or count their attempt timeout as their eventual durable latency.

Future TCP-specific adversarial additions include every split point of fixed prefix/body, coalesced frames, multiple pipelined calls, impossible/oversized declared lengths, partial headers/bodies, duplicate/colliding call IDs, response stalls, abrupt half-close/reset, auth expiry, cancellation before/after consensus handoff and process loss after durable apply but before response. Peer's framing contract supplies exact cases; this document introduces no competing frame layout.

Future HTTP-specific additions include headers/body trickle, stream reset and connection loss at each application boundary, malformed/duplicate framing metadata, disconnect during bounded streaming output, oversized decoded/base64 values, authentication/capability expiry, valid TLS but wrong authority/audience, retries/redirection and cursor continuation under projection lag. Peer's protocol profile determines HTTP/1 versus HTTP/2 framing and streaming details; this document introduces no endpoint inventory.

Cross-transport additions must retry one request across TCP and HTTP under its original request scope and obtain one persisted outcome; reuse its ID with different intent must reject; no-ID fencing compatibility must remain separate. Include missing/old scope, restore while queued/parked, scope preserved during forwarding and no automatic namespace change after lost response. Saturate one protocol/tenant/group while exercising the other and maintenance/Raft progress. Assert memory/count bounds, fairness, no queue leaks after timeouts, continued unknown-outcome recovery, no metrics credential leakage and real process/cluster failure behavior. Different local admission profiles must not cause replicas to apply the same committed entry differently. Property/model tests supplement rather than replace real faults and preserved cases. All are specified acceptance inputs only; no test implementation or execution is claimed.
