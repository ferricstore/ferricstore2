## Independent HTTP review

**TCP-H1 — schema drift, material interoperability issue.** HTTP initially uses `schema_version`, `command`, `attempt.timeout_ms` and flat consistency; TCP initially uses `schema`, `args`, `attempt_timeout_ms` and structured consistency. HTTP forbids body tenant whereas TCP requires scope in its body. Normalized digest alone cannot substitute for freezing the accepted schema. Parent's actual review message now selects common `schema_version: "1"`, `operation`, `tenant_id`, `request_id` for mutations, `args`, `attempt: {timeout_ms}`, and `consistency: {mode, after: {group_id, recovery_id, index}}`; create fields are `workflow_id/workflow_type/initial_state`. HTTP path tenant must match the required body tenant. TCP will adopt this selection; HTTP peer should confirm and correct its examples. Handshake `wf.v1` is an explicit label-to-schema mapping, not a second request version. Status: parent answered; both owned drafts need correction/confirmation.

**TCP-H2 — lookup must name recovery identity.** The route table only shows `?group_id=...`, while prose promises a specific stable recovery identity and replies return `recovery_id`. Require recovery identity in the lookup route/parameters and TCP query args; do not silently resolve an old request ID in the post-disaster namespace. Reject incompatible recovery identities explicitly. Status: question to HTTP/parent; proposed resolution is required `group_id` and `recovery_id`, including examples and restore tests.

**TCP-H3 — absence versus expiry needs honest evidence.** Lookup enumerates `expired`, but no bounded metadata policy explains how an unknown ID is distinguished from a once-retained expired ID. A missing outcome row cannot prove either historical existence or that an original in-flight attempt cannot commit. Please specify `expired` only when retained expiry metadata proves it, otherwise `not_observed` plus a retention-guarantee indicator (or explicit `retention_unknown`), with no safe-to-repeat claim. Exact tombstone/frontier retention is a shared application gate. Status: question to HTTP/parent; TCP will add the same qualification.

**TCP-H4 — non-submission is attempt-scoped.** Correct current text already says 401/403 means not submitted by this attempt. Please extend that statement to cancellation, overload, drain and all `not_submitted` responses: a rejected replay attempt does not cancel or disprove an earlier attempt with the same durable ID. This matters when the first TCP call loses its reply and a subsequent HTTP lookup/replay is unauthorized or cannot reserve memory. Parent's actual message selects OutcomeKind `applied/rejected/not_submitted/unknown/read` and SubmissionState `durable_outcome/not_submitted/may_have_been_submitted/not_applicable`; every HTTP/TCP wrapper should preserve the same pair, and clients must not infer request-wide rollback from attempt-local non-submission. Status: parent answered taxonomy; attempt-scope qualification requested from HTTP/system and to be added in TCP.

**TCP-H5 — long-poll finality is useful and must match TCP.** HTTP explicitly permits exactly one claim proposal per durable ID and treats a committed empty claim as final. Agree. TCP needs this detail, including dedup/reconciliation before deciding to park a retried claim and no automatic fresh-ID retry after unknown acquisition. A cancelled unsubmitted waiter yields a wait/attempt result, not a fake durable empty claim. Status: accepted HTTP design contribution; TCP correction planned.

No finding challenges HTTP's closed workflow scope, current authorization on replay, no-ID parity preservation, exact byte encodings, same-group atomicity, strong-read/projection distinction, trusted redirect policy or requirement to preserve original assertions. Those were actually read and are consistent with the shared contract.

## Independent system operations/conformance review

**TCP-S1 — profile count/deadline mismatch.** System proposes 16 executing + 8 queued per connection, a 5 s default attempt and 5 s-or-remaining write stall; TCP initially proposed 64 calls, 2 s default and a separate 30 s response write budget. Parent's actual message selects `max_active_calls=16`, `max_pending_calls=24` including executing/queued/parked calls, at most 8 queued, 5 s default and effective min of tenant/node/client bounds. Agree: TCP will use those numbers and a writer budget bounded by remaining attempt time. System should distinguish active, admission-queued and parked waiter counts, with their aggregate pending cap. A queue count is never permission to exceed the byte pool. Status: parent answered; TCP correction planned and system confirmation pending.

**TCP-S2 — parked waiters need a finite separate ledger.** System's table specifies active and waiting application work but leaves long-poll waiter counts, key footprint and wake work qualitative. Since waiters must not hold ordinary execution slots, declare an independent count/byte cap (or explicitly reuse the queued-work ledger while distinguishing the 10 ms admission queue deadline from longer wait time). Bound per-tenant/worker scope registration, wake fanout and authenticated recheck work; include parked calls in connection pending≤24. Suggested initial caps: 128 waiters/node, 64/group, 16/tenant, 8/connection, at most 16 registered scope keys per waiter and bounded wake dispatch; numbers remain unvalidated. Status: question to system/parent; exact finite policy still needed.

**TCP-S3 — pool sizes are shared maxima, not reserved per-connection capacity.** TCP's 4 MiB per-session ceilings cannot be preallocated for 1,024 connections inside a 64 MiB ingress/auth pool. Clarify lazy acquisition and one physical owner, including baseline connection/control/TLS overhead separately from body reservations. Likewise 256 active work slots times 1 MiB possible replies exceeds the 64 MiB response pool: admission must atomically apply the stricter count+byte limit; no guarantee of 256 simultaneous maximum-size replies. Parent's effective-min instruction helps but the system ledger should state these implications explicitly. Status: question to system/parent; TCP correction planned.

**TCP-S4 — reserved maintenance capacity and drain wording.** System correctly reserves lease/reconciliation capacity, but says reject new admissions first and later allow lease/reporting during drain. Define the node's drain admission classes: reject new ordinary/claim work, allow only bounded authorized maintenance/reconciliation until the shared service transitions to full stop, and remove parked claim waiters. The TCP listener cannot decide this business policy independently. Status: question to system/parent; TCP will reference shared phases rather than promise all new calls are rejected while maintenance continues.

System's p99≤50 ms statement is explicitly an unvalidated bounded workload target with rejected fraction and offered-load accounting. Agree with that separation; no latency guarantee or library-performance inference is established. The existing FIFO 80-follower requirement, fault-hook acknowledgement, count+byte accounting and continued submitted-operation ownership are correctly preserved.

## Parent common contract / ADR / architecture review

**TCP-P1 — make ordered lanes an explicit selected exception, without global order.** Parent correctly warns that general pipelining/HTTP concurrency does not imply ordering. TCP proposes a specific bounded serial lane policy: call N+1 may submit only after N has a definitive result; an uncertain submitted mutation stops that lane and queued later calls reject before submission. If selected, parent should name this explicit connection/lane-local policy and still deny cross-lane/cross-connection/global/FIFO inference. It is a scheduling policy, not Raft ordering authority. Parent's actual steering allows explicit ordering guarantees where established; TCP will retain this proposed policy and articulate its limit. Status: parent wording clarification pending.

**TCP-P2 — freeze taxonomy including read versus lookup state.** Accept parent's supplied outcome/submission pair. `read/not_applicable` describes an ordinary query; lookup's `not_observed/expired/unavailable` are result states, not fabricated mutation outcomes. Durable domain rejection is `rejected/durable_outcome` with retained record/position; edge denial is `not_submitted/not_submitted` for this attempt. Known late durable outcome beats unknown while client delivery may still fail. Status: parent selected vocabulary; own schema updates planned, shared examples/registry gate required.

**TCP-P3 — response size is a precommit service gate.** Parent and system correctly reserve worst-case output before submission. Handshake negotiated `receive_max_body_bytes` must constrain admitted result shape (including JSON/base64 envelope), not merely cause the socket writer to reject an already committed result. For too-small receivers, page supported queries or reject an indivisible mutation before proposal. No implicit chunking in FWTP/1. Status: consistency request to parent/system; TCP already contains this rule and will use effective caps in HELLO_ACK.

ADR and current architecture agree on the separate pure-wire/adapter crates and on adapter exclusion from raw ports/storage/consensus. No alternative crate dependency is justified by this review. Worker client adapters need a documented `wf-wire` dependency in their approved module graph, while retaining only client-facing port items; server adapters remain forbidden. This is a parent integration observation, not an edit to parent-owned files.
