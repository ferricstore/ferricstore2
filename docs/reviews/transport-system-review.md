## Parent questions answered through relay

- Maintenance is a slice of the 256 active slots and 64 MiB response partition; allocate at least 26 slots and 7 MiB inside those totals. It is not another 10% added to process limits. Per-tenant/group/connection sublimits still apply.
- Admission protects each node locally. Sending work to several nodes can multiply local allowance; a cluster-wide tenant entitlement is explicitly separate future work. Unknown outstanding work must remain accounted on the node that owns its submitted task.
- One actual claim proposal per durable ID: agreed with HTTP. An empty committed claim ends that ID; notifications do not authorize repeated proposals under it.
- Independent batches: agree with parent relay. No outer durable ID or implicit durable orchestrator; each ordered item has its own stable identity. Atomic_group owns one ID/digest for the full ordered intent and one same-group transaction.
- Canonical SHA256 typed version1 grammar belongs centrally. HTTP and TCP must decode to the same intent before hashing; no raw JSON hashing, cross-SDK loss of u64/bytes/zero or digest inclusion of attempt/call context.
