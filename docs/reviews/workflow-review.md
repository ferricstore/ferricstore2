## Findings for the architecture/plan author

1. **Atomicity boundary needs a deliberate parity decision.** Architecture says a logical partition is the atomicity boundary; inspected baseline tests establish rollback per Raft/shard group, including differently named partition keys colocated in one group. One-group/multiple-partition startup therefore does not imply that cross-logical-partition mutations must be rejected. Choose either narrower partition-local semantics as an explicit compatibility departure, or group-local atomicity with stable placement checks. M5's rejection of unsupported cross-partition operations currently conflicts with architecture's allowance of related changes in one consensus transaction. Prefer the baseline group-local boundary; never extrapolate to atomic cross-group operations.

2. **Preparation must not consume the claim decision.** Agree with pure preparation and apply-time revalidation. Prefer wholly authoritative, deterministic selection at apply for the initial design. A finite leader candidate list plus revision checks can miss a newly eligible higher-priority item or FIFO head even if every supplied candidate remains valid. Candidate validation alone cannot prove completeness. If that optimization is adopted later, specify an authoritative scope/version certificate or apply-time authoritative selection, and whether stale proposals reject the entire batch. This choice should be closed before M1 claim fixtures, not deferred until implementation discovers contention.

3. **Apply serialization and replay must be explicit.** `decide`, in-memory `apply`, and durable transaction commit must observe one ordered state per group. Do not let two commands decide from the same pre-commit state, or expose updated memory before persistence succeeds. On failed durable commit, stop/repair the replica rather than continue on advanced memory. Persist deterministic rejections, request outcomes, and applied positions as well as accepted mutations. Replayed already-applied entries must not create new fences/history. The ports describe atomic writes but leave read-view lifetime and apply-owner sequencing unspecified.

4. **Stable request digest must distinguish client intent from preparation.** CommandEnvelope adds explicit generated time/IDs, while request identity includes a stable command digest. Hash normalized client intent separately from regenerated preparation inputs, or retain the original prepared envelope on retry. Otherwise a redirected retry of identical intent can conflict with its own request identity. Unknown outcomes must reconcile with the same identity; do not reinterpret them as handler errors.

5. **Indexes and cache need separate terms.** Agree that cache is derived only. Persisted authoritative due/FIFO/ownership indexes are correctness structures even if mathematically derived from records; they must be transactionally consistent or rebuilt before enabling apply. Disposable query/payload caches and lagging projections cannot decide eligibility. Domain may use a consistent authoritative index through its bounded read view; 'no cache decides FIFO' should not prohibit all indexing or imply scanning every workflow.

6. **Trait ownership remains underspecified.** Keep semantic storage traits in ports; keep OpenRaft trait implementations on consensus-owned local bridge/newtype adapters wrapping those ports. Node wires them and owns lifecycle, not storage/Raft semantics. That respects the canonical allowlist without adding a bridge crate by default. If node-owned wiring modules implement substantive consensus/storage logic, composition-root isolation is lost. Define coherent snapshot read and transaction read/write capability together; a write-only StateTransactionPort cannot establish the consistent input view required by decide.

7. **Crate count is an upper bound, not a requirement.** Eleven crates are reasonable only where differing dependency sets or visibility justify them. Domain/adapter separation is mandatory; shared dependency sets can use separate checked modules. Keep worker independently reusable and keep test tooling outside runtime. Defer a dedicated HTTP-client or bridge crate until it has a real ownership/dependency need. Do not merge everything merely to reduce count, but do not invent empty crates to match the table.

8. **Scope gates must stay visible.** Governance, approvals, budgets, durable effects, and durable steps need named supported/deferred/dropped decisions before calling this workflow parity. Signals/schedules are proposed scope pending source mapping. Basic Elixir SDK parity does not settle the broader Python effect/step contract. Put these decisions in the preimplementation parity gate and milestone table; no omission is implied by 'workflow-only.'

### Answers to Darwin's questions

**FIFO and partial claims.** Initial claims now select from authoritative state during apply, eliminating stale prepared candidate sets. A partial claim may contain fewer jobs than requested when its scan budget ends, but it must not skip the live head of a FIFO lane to claim a later member of that same lane. It may select heads of other eligible lanes according to the frozen total ordering. Continuation is an advisory resume position, not ownership or eligibility proof; the next command must revalidate authoritative lane state. Empty-with-continuation must differ from exhausted/no eligible work. Baseline evidence establishes lane identity by type + logical state + partition, sequence encoded as unsigned big-endian 128-bit followed by ID, and running records retaining `run_state` lane membership: [FifoLane at the committed baseline](https://github.com/ferricstore/ferricstore/blob/66586c596e271408d9184af32eb31cd7218c126e/apps/ferricstore/lib/ferricstore/flow/fifo_lane.ex). This source does not alone prove all scan/partial semantics; those are proposed rules to freeze in M1 fixtures, with a remaining audit of claim selection and priority interaction. Do not advertise full FIFO parity from this helper alone.

**Idempotency before guards.** Yes: revised architecture explicitly checks tenant + group + request identity and canonical client-intent digest before changed lease/revision preconditions. A matching retained outcome returns the original acceptance or deterministic rejection. A mismatched digest rejects request-ID reuse; it must not overwrite the original outcome. Missing/expired dedup records follow the documented expiration contract, not a claimed indefinite exactly-once guarantee. Current authorization still applies before exposing a stored result; dedup does not bypass tenant access checks.

**Canonical client-intent normalization.** Proposed schema gate: digest a versioned typed representation after syntactic validation, with stable field ordering and explicit discriminants. Preserve opaque ID, token, partition and payload bytes exactly; no Unicode/case normalization or JSON reserialization of opaque payload. Include command kind, resolved target/tenant scope, submitted state/lease/fence/revision guards, payload/reference identity, policy override, scheduling inputs, limits and any caller-specified time/IDs. Exclude transport credentials, tracing, retry count, leader routing hints and leader-generated time/IDs/jitter. Default normalization must be defined by the digest schema version: implicit and explicit defaults are equivalent only where the contract says so, and server policy changes must not silently alter an existing request's digest. Batch order is meaningful where response order or mutation semantics depend on it and must be retained. Reject duplicate JSON fields and non-finite/ambiguous numeric input before hashing. Digest format/hash choice is still an ADR gate, not an implemented codec; pin golden vectors across SDKs. Immutable prepared-entry identity remains separate.

**Governance/effect/step dispositions.** Their final product disposition is still open, as requested. Proposed staging for approval: defer approvals, budgets and broader governance from M4; inventory each public command and authorization invariant at the parity gate; reject unsupported operations explicitly. Durable effects and durable steps are a separate SDK/runtime compatibility gate, with proposed deferral from the minimal slice, not a permanent drop. If included, effect reservation/reconciliation and step outcome-unknown behavior require dedicated milestones and tests; an ordinary claim/result worker does not implement them. No blanket 'full workflow parity' claim is acceptable before the parent chooses supported/deferred/dropped dispositions command by command.
