## Ownership and atomicity

Follow the [canonical architecture](../architecture.md): neutral log, authoritative transaction/read-view and snapshot contracts live in `wf-ports`. Local bridge types in `wf-consensus` implement the selected OpenRaft traits and translate framework values to neutral values. `wf-storage` implements the neutral ports; `wf-node` wires concrete instances and lifecycle. No storage-to-consensus dependency, OpenRaft types in domain/ports, or workflow decisions in node glue. Rust's local wrapper ownership makes this a plausible layout; no selected-version trait constraint has been demonstrated or ruled out. An additional bridge crate requires a concrete constraint and ADR, not speculation.

A Raft group is the transaction boundary. Commands may atomically touch several logical partitions only after authoritative placement confirms the same group and bounded write set. The workflow peer reports group-local baseline rollback semantics; this review accepts the parity recommendation but did not independently inspect those tests. Cross-group parent/child updates and fanout are rejected until a separate saga exists. Placement is versioned, server-validated state; client hints cannot establish atomicity. Initial live group migration is unsupported.

## Single ordered authoritative apply

One apply owner per group processes committed entries in order. Its transaction capability includes a coherent authoritative read view, bounded ordered range reads and atomic writes, not merely a write batch. Entry N+1 cannot decide while N has an uncommitted write set. Either the backend transaction supplies that view directly or the adapter proves a serialized immutable view tied to the persisted checkpoint. Do not split a decision across unrelated read snapshots.

For each entry: verify entry ordering/identity; consult retained request outcome; decide deterministically against the coherent view; commit the complete accepted transition or deterministic rejection; then publish memory and reply. Atomic persistence includes records, policies, ownership/due/FIFO indexes, fences, durable history/events, idempotency digest and outcome, logical time, applied membership where applicable, and last-applied log identity. Membership and other non-workflow entries advance the checkpoint through the same ordered path. No accepted result is acknowledged from memory alone.

A deterministic rejection changes no workflow business state but durably records the rejection and applied checkpoint. Request-ID reuse with different intent must preserve the original dedup record; the conflict response is deterministic and its entry advances last-applied atomically. An equivalent duplicate returns the original outcome without another fence/history event while the new log entry still advances its checkpoint. Already-applied log entries are recognized by durable log identity, not index alone, and never re-execute mutations. Original outcome position and current processing position must remain distinguishable.

Disk-full, corrupt reads, failed transactions and inconsistent checkpoints are operational storage failures, never empty views or `DomainError`. A known aborted transaction can retry the same entry with unchanged published state. An uncertain commit requires durable reconciliation before retry; an unreconciled or corrupt replica stops serving/applying. Never skip an entry, advance last-applied on failure, or continue from speculative memory. Restart derives authority from durable state and resumes ordered replay.

## Claims and identity

Initially replicate a bounded claim request, then select at apply from transactional authoritative indexes. Freeze tenant/scope, lane identity, priority/FIFO ordering, tie-breaks, lease duration, scan budget and explicit time semantics before M1. Range/prefix reads must include the authoritative lane heads and exclude phantom changes by sharing the apply transaction/view. A leader's candidate revision checks cannot certify an omitted earlier candidate; hints are deferred.

Budget exhaustion has an explicit partial/continuation outcome distinct from no eligible work. A live FIFO head cannot be skipped for a later member in that lane. Other eligible lane heads may be selected according to the frozen total order. Continuation is advisory and must be revalidated; it cannot authorize work. Index updates and fence allocation are in the same transaction as each claim. Fence counters cannot reset on restart, leader change or snapshot installation; exhaustion rejects deterministically rather than wrapping.

Dedup scope is tenant + group + request identity. Canonical versioned client-intent digest preserves opaque bytes, submitted guards and meaningful batch order; excludes credentials, tracing, routing hints and leader-generated time/IDs/jitter. Define defaults and reject ambiguous input before digesting; cross-SDK vectors remain a future gate. Prepared entry identity separately covers its immutable committed inputs. Check dedup before changed lease/revision guards. Retained matching requests return their original accepted or rejected outcomes, subject to current tenant authorization. Timeouts are unknown outcomes reconciled with the same identity. Retention explicitly bounds this guarantee. Future placement migration must move dedup/routing atomically or preserve an authoritative redirect/lookup; it cannot silently create a fresh request namespace.

## Durable vote and log contracts

Neutral ports must express the selected adapter's vote identity, ordered log identities, entry payload/version, truncation/purge boundaries and error classification losslessly. Persist votes and log appends before reporting the durability completion required by the selected OpenRaft API; enforce its ordering and monotonic vote rules. Buffering or a completed write syscall alone is not a durable acknowledgment. The spike must map completion callbacks, fsync/WAL guarantees and crash recovery explicitly.

Conflicting suffix replacement must be crash-safe, preserve committed/applied entries, and report failures. Purge only through a recoverable snapshot/applied boundary satisfying the chosen Raft contract. Retain durable purged-log metadata, applied position and membership so restart cannot mistake removed history for an empty cluster. Partial/torn records or invalid continuity produce a recovery error, not fabricated entries. Vote/log durability and state-machine atomicity are distinct obligations; no single transaction across every Raft and workflow operation is assumed. Their recovery invariants must be demonstrated before adoption.

## Snapshots and installation

Create a snapshot from one committed authoritative read version at an exact applied log identity. Concurrent apply may continue only if the backend offers a pinned coherent view; otherwise pause the ordered owner for capture. Include format/schema and group identity, last-applied log identity, effective applied membership, workflow/policy/placement state, replicated logical time, lease/fence high-water marks, retained dedup outcomes/digests, durable history and rebuild metadata, and authoritative correctness indexes. Include inline payload/results; future blobs require a complete verified manifest and recoverable bytes. History/outcome retention boundaries must be explicit so restore does not invent stronger retention guarantees.

Disposable caches and projections need not be serialized. Authoritative indexes may be rebuilt from the captured state only through a deterministic bounded recovery procedure completed before claims or authoritative service resumes. A snapshot manifest must declare whether indexes are included or require rebuild. Checksums establish integrity, not trust or semantic validity.

Install into an isolated staging generation with bounded decoding/resources. Verify group identity, schema compatibility, applied/membership consistency, manifest/chunk checksums, completeness, fence/dedup/history/index invariants and blob availability. Never overwrite active files incrementally. Coordinate with the apply owner so stale snapshots cannot roll back active state and concurrent entries cannot be lost. Flush staging data/metadata and atomically activate a durable generation pointer or equivalent backend transaction; account for filesystem directory durability if used. A crash must recover either the old complete generation or the new complete generation, never a mixture. Snapshot activation, checkpoint and membership become visible together; exact integration with log purge follows the selected Raft API.

After activation, invalidate cache generations, fence old projection checkpoints, rebuild/verify authoritative indexes and reopen reads only on the activated view. Old generations are reclaimed after successful recovery/activation and reference release. Corrupt/incomplete staging is rejected without destroying the active generation. These are required properties, not tested backend capabilities.

## Time, payloads and reads

Replicated explicit time makes apply deterministic; it does not make physical clocks accurate. Proposed Rust design maintains nondecreasing group logical time from committed inputs and uses it for domain deadline comparisons; IDs/jitter are also explicit. Backward wall jumps cannot decrease domain time. Advancing time requires committed commands/ticks, so an idle cluster needs a bounded tick policy for expiration progress. A large forward jump may prematurely expire physical-time leases. Before deployment choose a clock trust/skew envelope and admission policy for jumps/new leaders; halt time advancement or service outside that envelope rather than claiming safe real-time expiry. Jump thresholds and externally visible scheduling semantics remain open. Logical ordering and fencing prevent stale state mutations; they do not stop an old worker's external side effects. External systems must enforce fences/idempotency where needed.

This time policy is a candidate under the time ADR gate, not proven legacy HLC/wall behavior or a finalized clock algorithm. Caller-specified timestamps do not implicitly authorize advancing group time or expiring leases. The ADR must specify timestamp trust/admission and the time-advance rule for accepted, rejected, duplicate, tick and membership entries. A rejected command may change only explicitly permitted control metadata; its outcome and checkpoint are durable regardless of whether that rule advances time. Duplicate processing must preserve the original outcome/time-dependent result even if a new entry advances the processing checkpoint or permitted group time. Membership cannot obtain an unstamped local clock input during apply. Fixtures must freeze each case before implementation.

Start with bounded inline payload/results in replicated commands and snapshots. Reject oversized requests explicitly. Deferred blobs require proof that bytes survive leader loss and are available to every eligible applying replica and snapshot recipient before a reference can become authoritative. Local preupload or the leader's cache is insufficient. Specify replicated availability acknowledgment, immutable digest/length, missing-byte recovery, retention/GC roots and snapshot transfer before enabling references. Avoid hydration/network I/O in the reducer; adapter preconditions must preserve ordered apply and bound queues. Missing authoritative bytes cannot become a fabricated business rejection.

Strong reads establish a selected-version leader/quorum read barrier and wait until durable apply reaches its required position, then read a coherent authoritative view. Leadership uncertainty returns unavailable/redirect; a local applied counter alone cannot certify linearizability. Authenticate before exposing data; cached values additionally require matching tenant, record revision and schema from that view. Release guards before await.

Projection checkpoints identify group, recovery generation/epoch, applied log position and projection schema. Events and checkpoint advance atomically in the projection's own store; durable authoritative events permit replay after notification loss. A projection cannot advance beyond incorporated events. Read-your-write waits for the requested comparable watermark or returns a documented lag/unavailable result. Cross-group or generation-incompatible watermarks require explicit reconciliation, not numeric comparison. Lists/history must declare their consistency and pagination snapshot contract; never advertise lagging projections as linearizable.

Separate stable authoritative group/cluster and log outcome identity from projection-local build generation and cache generation. Ordinary restart preserves authoritative identity and retained write positions; a lost/rebuilt projection gets a new local generation. Snapshot install preserves authoritative identity only for the same valid Raft lineage, while invalidating incompatible derived generations. A rebuilt projection may honor an older write watermark when its durable checkpoint and lineage demonstrate incorporation, even though its local generation differs. Otherwise return lag, incompatible or unavailable explicitly; never compare bare indexes or invalidate every old write token merely because a cache restarted. Disaster restore creates a new recovery identity/lineage and returns an explicit incompatible-position result for old client positions, as required by the canonical architecture. Exact token encoding, incorporation proof and lifecycle transitions remain the watermark/restore ADR gate.

## Membership, recovery and validation gates

Bootstrap a new group only through explicit empty-store/cluster identity checks; restarting an existing member must recover its durable vote, log, snapshot, applied state and membership. Use the selected Raft implementation's learner catch-up and membership transition protocol, serialized with applied membership; do not hand-roll quorum changes. Never count a new node as ready solely because it received metadata: it needs recoverable state/payloads. Removed members cannot acknowledge as current leaders; endpoint discovery is distinct from voting membership. Minority partitions cannot complete quorum writes or strong reads.

Recovery verifies checkpoint/log/snapshot compatibility and replays the retained committed suffix through the single owner. Uncommitted suffix handling belongs to Raft. Backups carry a coherent recoverable generation and manifest, not arbitrary files copied at different times. Disaster restore/forced rebootstrap needs a separate operator procedure and new cluster/recovery identity that prevents old members, watermarks and external fence namespaces from being reused unsafely. Do not reset fences under an old identity.

Remaining gates: select release/backend together; demonstrate bridge trait mapping, durable vote/log completions, atomic accepted/rejected apply and uncertain-commit reconciliation; freeze claim/digest/time rules; validate capture/install and restart/purge recovery; prove read barriers and membership transitions; test lost replies, disk failures, pauses/partitions, cache-disabled operation and projection rebuild. These are planned M1–M3/M6/M7 evidence, not conformance results. See the [file review and peer replies](../reviews/raft-storage-review.md).
